# Zabbix Web UI


## 1. 設定ファイルと Web UI の分担

Zabbix では、**設定ファイルはデーモンの動作のみを規定し、監視の内容はすべて Web UI（実体はデータベース）で設定する**。

| 設定場所 | 設定内容 |
| --- | --- |
| `zabbix_server.conf` | DB 接続先、待受ポート、プロセス数、ログ出力先 |
| `zabbix_agent2.conf` | 通信相手のサーバ、自身のホスト名 |
| Web UI（DB） | ホスト、アイテム、トリガー、アクション、通知、ユーザー、権限 |

監視対象を追加しても設定ファイルは変更されない。この分担は Cacti と同様であるが、以下の点が異なる。

| 観点 | Cacti | Zabbix |
| --- | --- | --- |
| データ保存先 | RRDtool ファイル | データベース（テーブル） |
| しきい値監視・通知 | プラグイン（Thold 等）が必要 | トリガー・アクションが本体機能 |
| 設定の再利用 | グラフテンプレート | テンプレート（アイテム・トリガー・グラフを含む） |

データベースに保存する方式は SQL で直接参照できる利点がある一方、データ量が増加するため保存期間の設計（Housekeeping）が必要になる。

なお Zabbix には JSON-RPC の API が用意されており、ホスト登録やテンプレート適用をスクリプトから実行できる。テンプレート自体も YAML / XML でエクスポート・インポートが可能であるため、多数のホストを扱う場合は画面操作ではなく API またはテンプレートインポートを用いる。

エージェント側の `Server` と `Hostname` は監視対象ごとに配布が必要なファイル設定であり、ここは構成管理ツールの適用対象となる。

## 2. Web UI の基本操作

画面は「見る場所」と「設定する場所」が明確に分かれている。この対応を把握しておくと迷わない。

### 2-1. メニューの構成

| メニュー | 役割 |
| --- | --- |
| **Monitoring** | 見る。現在の状態・値・グラフ |
| **Data collection** | 設定する。ホスト・テンプレート・アイテム・トリガー |
| **Alerts** | 通知する。誰に・いつ・どうやって送るか |
| Reports | 集計。可用性レポート、トップ100など |
| Users | ユーザーと権限 |
| Administration | システム設定。データ保持期間（Housekeeping）など |

### 2-2. よく使う操作

**今どうなっているか見る** ―― `Monitoring → Problems`

発生中の障害が一覧表示される。運用中に最も開く画面である。

**値を見る** ―― `Monitoring → Latest data`

ホストとアイテム名でフィルタして実測値を確認する。項目を選んで `Display graph` でグラフ化でき、複数選択すれば重ねて表示できる。

`Execute now` **を押すと、次の収集タイミングを待たずに即座に取得**できるため、設定変更直後の確認で多用する。

**グラフを見る** ―― `Monitoring → Hosts` → 対象ホストの `Graphs`

テンプレート付属のグラフが並ぶ。右上で表示期間を変更できる。

**監視対象を増やす** ―― `Data collection → Hosts` → `Create host`

設定するのは4項目。Host name（エージェント側の `Hostname` と一致させる）、Templates、Host groups、Interfaces（IP とポート 10050）。

Host groups は必須項目なので未入力だとエラーで止まるが、**Templates は任意項目なので黙って登録が通る**。その結果「ホストは作れたのに値が入らない」となるのが定番の失敗である。

付け忘れは一覧画面で判別できる。

| 状態 | テンプレートあり | テンプレートなし |
| --- | --- | --- |
| Tags | `class: os` などが自動で付く | 空 |
| Graphs / Dashboards | 件数付きのリンク | 灰色 |
| ZBX | 緑 | 灰色のまま |

テンプレートを後から追加する場合は、ホスト名をクリックして設定画面を開き、`Templates` 欄に入力して `Update` する。保存した時点でアイテム・トリガー・グラフがそのホストにコピーされる。

**しきい値を変える** ―― `Data collection → Hosts` → 対象の `Triggers`

ただし**テンプレート由来のトリガーは、そのホスト単体では編集できない**。テンプレートを修正すると適用中の全ホストに反映される。1台だけ変更したい場合は、次のマクロによる上書きを用いる。

**マクロで上書きする** ―― ホストの `Macros` タブ

テンプレートのしきい値は `{$CPU.UTIL.CRIT}` のようなマクロで記述されている。ホスト側で同名のマクロに別の値を設定すると、そのホストだけしきい値が変わる。**テンプレートを壊さずに個別調整する標準的な方法**である。

**通知を止める** ―― `Data collection → Maintenance`

メンテナンス期間を登録すると、その間アラートが発報されない。計画作業時に用いる。

### 2-3. 通知の仕組み

通知は3つの設定が揃って初めて飛ぶ。ここが最初につまずきやすい。

- `Alerts → Media types` … 送信手段（Email / Slack / Webhook）を定義・有効化
- `Users → 対象ユーザー → Media` … 宛先（誰のどのアドレスへ）
- `Alerts → Actions` … いつ送るか（どのトリガーが発火したら）

**Media types は既定で Disabled になっていることが多く**、有効化を忘れて「トリガーは上がるのにメールが来ない」となるのが定番の失敗である。

### 2-4. 早見表

| やりたいこと | 場所 |
| --- | --- |
| 障害一覧を見る | Monitoring → Problems |
| 値の確認・即時取得 | Monitoring → Latest data |
| ホストを追加する | Data collection → Hosts → Create host |
| テンプレートの中身を見る | Data collection → Templates → 対象 → Items / Triggers |
| しきい値を1台だけ変える | Data collection → Hosts → 対象 → Macros |
| 通知が飛ばない | Alerts → Media types が Enabled か確認 |
| 計画作業で通知を止める | Data collection → Maintenance |
| データ保持期間を変える | Administration → Housekeeping |

全体の流れは **ホストを作る → テンプレートを貼る → アイテムが値を取る → トリガーが判定する → アクションが通知する** という一本道である。

画面数は多いが、この鎖のどこを操作しているかを意識すると整理できる。
