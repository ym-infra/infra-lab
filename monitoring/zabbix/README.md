# Zabbix

監視ツール Zabbix 7.0 LTS を、コンテナを使わず手動で構築し、Linux・HTTP・Docker・SSL 証明書の監視を設定した際の作業記録。

Docker / Kubernetes の学習の一環として、コンテナで動くサービスをどう監視するかを確認する目的で構築した。

## 環境

| 役割 | OS | 用途 |
| --- | --- | --- |
| Zabbix サーバ | AlmaLinux 9 | 監視する側。Zabbix 7.0 LTS / MariaDB / nginx / php-fpm |
| 監視対象 | Amazon Linux 2023 | 監視される側。Docker Compose で WordPress + MariaDB + nginx proxy が稼働 |

いずれも AWS EC2。監視サーバと監視対象は分けている。同一ホストで兼ねると、障害を起こす演習で Zabbix の画面自体が落ちてしまうため。

## 整理したこと

- **Zabbix の構成要素** — Server / Web(PHP) / DB / Agent の4つに分かれており、Web UI と Server は直接通信せず、どちらも DB を読み書きする
- **監視の流れ** — ホスト → テンプレート → アイテム → トリガー → アクション。アイテムは値を集めるだけで、判定はトリガー、通知はアクションが担う
- **パッシブとアクティブ** — `Server=` は許可リスト、`ServerActive=` は接続先。Nagios とは用語の向きが逆になる
- **LLD** — 数が事前に分からない対象（コンテナ、ファイルシステム）を自動検出して監視項目を生成する。Cacti の Data Query が近いが、生成まで自動な点が異なる
- **監視のレイヤ** — ホスト OS / 外形 / コンテナ / 証明書で見えるものが違う。DB コンテナを止めても、WordPress コンテナは `Up` のまま外形監視だけが落ちる
- **TLS 終端の位置** — 証明書はアプリのコンテナではなく前段に置く。nginx proxy ≡ ALB ≡ Kubernetes Ingress

## 他の監視ツールとの比較

以前に Nagios と Cacti を構築した経験と比較しながら整理している。エージェントの許可リスト、閾値の持ち方、自動検出の考え方など、同じ概念が別の名前で出てくる箇所が多い。
